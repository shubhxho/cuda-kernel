# RTX 5060 assessment for these kernels

This is an evidence-backed read of how the kernels in this repository would behave on a GeForce RTX 5060. It is **not** a benchmark result.

**Assumption (prominent):** the repository does not name a 5060 variant. Numbers below that say "desktop RTX 5060" mean the **desktop** GeForce RTX 5060 in NVIDIA's 5060 family spec table. The laptop GPU is a different product: fewer CUDA cores, a published 384 GB/s memory spec, and OEM-dependent clocks and power. Do not treat laptop 5060 and desktop 5060 as interchangeable.

No process in this workspace ran on an RTX 5060. No latency, speedup, or "X times faster than Y" figure in this file is a measured 5060 result. Rows labeled **ESTIMATE** or **analytical lower bound** are not predictions of wall-clock time.

## Verdict

For the actual workload (batch-one, FP16 weights, FP32-accumulate GEMV / fused SwiGLU decode):

- **Good fit:** TinyLlama-1.1B and the synthetic single-layer shapes. They are weight-streaming and memory-bound. 8 GB is enough for TinyLlama plus the decode working set. Aligned hidden/intermediate sizes can use the 128-bit vector path.
- **Poor fit:** full Llama-2-7B or Llama-3-8B in FP16. Those models are larger than 8 GB. This repo has no quantization path. The `decode-7b-shape` and `decode-8b-shape` cases are **one FFN layer**, not those full models.
- **Unused hardware:** the custom kernels are CUDA-core FP32 FMAs after FP16 loads. They do not call tensor cores. NVIDIA's 614 AI TOPS desktop figure is the wrong unit for this code. Do not scale expected kernel time from TOPS.
- **Custom vs cuBLAS:** not knowable from specs. Both paths read essentially the same weight bytes. Fusion saves two kernel launches and tens of kilobytes of intermediates, which is small next to tens or hundreds of megabytes of weights. A library GEMV can still win. Only a 5060 run of `decode_bench` can call a win.

Numerical kernel latency on a 5060 **cannot defensibly be estimated** from this repository. There is no measured GPU sample here, and no calibrated achieved-bandwidth fraction for these kernels. What can be stated is an analytical DRAM lower bound: time cannot be below `bytes / peak_bandwidth` if the kernel streams those bytes once.

## What the repo actually implements

Precision and paths (see `include/kernels.cuh`, `src/benchmark.cu`, `src/torch_extension.cu`):

| Path | Weights / input | Accumulate | Hidden | Output |
|---|---|---|---|---|
| Standalone custom projection | FP16 | FP32 FMA | n/a | FP32 |
| Standalone custom SwiGLU | FP16 | FP32 FMA | FP16 | FP32, residual added in the down kernel |
| cuBLAS baseline | `cublasGemmEx` FP16 in, `CUBLAS_COMPUTE_32F`, default or `CUBLAS_GEMM_DEFAULT_TENSOR_OP` | FP32 | FP16 after epilogue | FP32 plus residual kernel |
| PyTorch model binding | FP16, `MODEL_ROUND` matches eager Linear/SiLU/mul rounding | FP32 inside the kernel | FP16 | FP16 |

Ten launch configs: warps per row in {1,2,4,8}, rows per block in {1,2,4,8}, pack 2 (half2) or pack 8 (128-bit PTX `ld.global.v4.u32`). No WMMA, no `mma.sync`, no INT8/FP8/FP4, no attention kernel.

Build targets today:

- Host tests: C++17, no CUDA.
- CUDA build: CUDA 12.0+ toolkit required by CMake; README examples use 12.6.
- GitHub compile job (CUDA 12.6.3 image): cubin for 75, 80, 86, 89, 90, plus `90-virtual` PTX.
- Native RTX 5060 cubin is **sm_120**. That needs CUDA 12.8+. `make blackwell` passes `-DCMAKE_CUDA_ARCHITECTURES=120`.

Modal's documented worker is an L4 (Ada, SM 8.9), not a 5060.

## Arithmetic intensity (actual kernels)

A projection `y[rows] = W[rows, cols] @ x[cols]` with FP16 W/x and FP32 output does `2 * rows * cols` FLOPs and reads `rows * cols * 2` weight bytes. The weight term dominates. Intensity is about **1 FLOP/byte**.

Ridge-point sketch, labeled **ESTIMATE** because peak FP32 TFLOPS is derived from published cores and boost, not a NVIDIA "TFLOPS" cell:

```text
ESTIMATE desktop FP32 FMA peak = 3840 cores * 2 * 2.50 GHz = 19.2 TFLOPS
Ridge FLOP/byte at 448 GB/s     = 19.2e12 / 448e9 ≈ 43
```

1 FLOP/byte is far below 43. These decode shapes are DRAM-streaming, not compute-streaming, unless the working set fits and stays in cache. A TinyLlama FFN layer is about 69 MB of weights. NVIDIA does not publish 5060 L2 size on the product page; `decode_bench` records `l2_bytes` from `cudaDeviceProp` when a GPU is present. Do not assume the layer stays in L2 across 22 layers.

Fusion (gate+up+SiLU in one launch, residual in the down launch) does **not** change the weight traffic. Against three cuBLAS GEMVs it avoids extra FP32 intermediate write/read on the order of `2 * intermediate * 4` bytes (64 KiB at TinyLlama width). That is <0.1% of the FFN weight bytes. Launch count (2 vs 5) matters more on the smoke shape than on the 8B-layer shape.

Generated byte counts and 100% peak-bandwidth floors: [rtx-5060-bounds.md](rtx-5060-bounds.md), regenerated by `python3 tools/intensity.py`.

## Analytical lower bounds, not predictions

`t >= bytes / peak_bandwidth`, one streaming pass, zero launch cost, 100% of the named peak. Real kernels are below peak, so measured time should be **above** these floors. These floors are not a forecast of median latency.

From `tools/intensity.py` (also in `docs/rtx-5060-bounds.json`):

| Shape | Custom FFN bytes | Lower bound at 384 GB/s (NVIDIA laptop) | Lower bound at 448 GB/s (derived desktop) |
|---|---:|---:|---:|
| smoke | 3 159 040 | 8.227 µs | 7.051 µs |
| tinyllama-1.1b | 69 271 552 | 180.395 µs | 154.624 µs |
| decode-1b-shape | 100 749 312 | 262.368 µs | 224.887 µs |
| decode-7b-shape | 270 661 632 | 704.848 µs | 604.155 µs |
| decode-8b-shape | 352 477 184 | 917.909 µs | 786.779 µs |

Projection-only floors are about one third of the FFN floors (one weight matrix instead of three).

Unverified efficiency envelope, **not** a 5060 estimate: if someone assumed 50% to 90% of peak bandwidth, kernel-only time for the same byte count would be `1/0.9` to `1/0.5` times the 100% floor (about 1.11x to 2x). This repo has **no** measured efficiency on any NVIDIA GPU, so that envelope is not calibrated and must not be quoted as expected 5060 latency.

Launch and CUDA-graph overhead are omitted from the floor. They can dominate the 7 µs smoke bound. They are a small fraction of the 0.8 ms 8B-layer bound.

Host/device transfers of the token vector are a few kilobytes. At PCIe 5 (desktop 5060 is listed as PCI Express Gen 5 on NVIDIA's table) that cost is small next to weight streaming. Cold upload of the weights is not the decode path; the benchmark keeps weights resident. `decode_bench --include-transfers` times pinned H2D of x, the kernel graph, and D2H of the output with weights still resident.

## VRAM

Desktop and laptop 5060 both advertise **8 GB**.

| Workload | Fit on 8 GB? |
|---|---|
| One synthetic FFN layer, including 8B-shape | Yes (working set 0.3 GB) |
| TinyLlama-1.1B-Chat-v1.0 FP16 (~2.2 GB download in README) plus short KV cache | Yes |
| Full Llama-2-7B FP16 (~13 to 14 GB weights) | No, without offload or quantization (neither is in this repo) |
| Full Llama-3-8B FP16 (~16 GB weights) | No |

`decode-7b-shape` / `decode-8b-shape` succeeding on a 5060 would not mean those full models run.

## When this is good or bad on a 5060

Good (relative to the kernel's design, not vs a library):

- Batch-one decode of a model that fits, especially TinyLlama.
- Hidden and intermediate multiples of 8, 16-byte aligned pointers: pack-8 path.
- Timing after warmup, weights already on device, graphs captured: this is what `decode_bench` reports as kernel-only.

Bad or misleading:

- Using 614 TOPS or 58 RT TFLOPS to "compute" MLP latency.
- Expecting tensor-core speedups from the custom kernels (there are none in the source).
- Prefill or batched tokens. The binding rejects anything but single-token, batch-one.
- Full 7B/8B FP16 models in 8 GB.
- Laptop SKUs at the bottom of the 1455 to 2497 MHz range, or low OEM TGP. Bandwidth-bound kernels track memory clock and sustained bandwidth, not peak TOPS. NVIDIA's laptop bandwidth is already 384/448 ≈ 86% of the derived desktop figure **if** both hit their published/derived peaks. Low-power SKUs may sit below that. That ratio is an **ESTIMATE** of peak-spec scaling, not a measured laptop/desktop speedup.
- Model-level speedups. Attention, KV cache, RMSNorm, and Python still run. README already says a faster MLP need not make TinyLlama faster.
- Board partner clocks, Resizable BAR off, a busy display engine, or power limits. Record them; do not assume the 145 W / 2.50 GHz row.

## How to measure on a real 5060

See [benchmark.md](benchmark.md). Short path:

```sh
# CUDA 12.8+ recommended for native sm_120
python3 tools/run_bench.py --arch 120
# Optional TinyLlama (downloads weights; needs PyTorch CUDA 12.8/12.6 wheel that supports the driver)
python3 tools/run_bench.py --arch 120 --model
```

A result is a 5060 measurement only if `gpu` in the JSON is a 5060, `result_class` is `measured`, and `compute_capability` is `12.0`. Copy that JSON into `results/` and render with `tools/report.py`. Do not paste those numbers back into this file as "estimates".
